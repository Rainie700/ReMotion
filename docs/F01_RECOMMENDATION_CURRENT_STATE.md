## 0. 實際流程（現行程式）

```
首次五次坐站（result.status / totalDurationMs / 量測版本）
 └─ Phase C 首次推薦：選目標 G01–G05、可用時間、勾選限制 L01–L05
      generateF01GoalRecommendation → 1–3 個動作（不讀秒數）
      └─ 建立 7 日追蹤週期（Day 1–6 訓練，Day 7 起可再評估）
           └─ 訓練：每天凍結當日動作與目標量 → 相機紀錄單筆達標才算該動作完成
                → 當天全部動作完成才記 1 個完成日（completedTrainingDates）
                （每日吃力／不適／未完成原因、自行回報：另存，不進入判定）
           └─ 再評估 → D4 比較（eligible、changeMs = 再評估 − 初次，原始毫秒）
                └─ D5 狀況確認：有沒有新的或加重的不適（是／否）＋重新勾選 L01–L05
                     └─ buildD5Proposal：Gate 1–5 判定 → Gate 6 選動作 → Gate 7 確認方式
                          └─（選用）LLM 草稿：預設關閉，有草稿就一律要復健師確認
                          └─ resolveD5Arrangement：ready / needs_review / reviewed / no_auto
                               └─ 復健師檢視（needs_review、no_auto）
                               └─ 患者接受（只有 ready、reviewed 可以）
                                    └─ 下一週：同日沿用再評估作基準，否則先做新基準評估
```

## 一、資料實際用途

「目前是否參與推薦」一欄只用三種標記：
- **實際參與判定**：數值會改變推薦動作、判定結果、是否能接受，或是否能開始下一週。
- **僅供顯示／復健師查看**：會出現在畫面上，但不改變任何判定。
- **已儲存**：有存下來，但沒有畫面用到，或只在選用功能中使用。

### 2-2 哪些評估數值真的影響動作選擇

- **首次推薦**：五次坐站只當「是否完成」的閘門。秒數、每下時間、拒絕次數**都不影響選哪個動作**。選動作的是：目標、限制、時間（只決定數量）。
- **D5**：秒數只透過 `changeMs` 的三分類進入矩陣，再加上完成天數，產生「維持／進階／調整／不自動判定」。
  - 會實際換動作的情況只有兩種：**進階且有可用轉換**，以及**限制排除了 1 個現有動作**。
  - 唯讀模擬（無限制、從系統首次推薦出發，5 目標 × 3 時間選項）：判定進階時，**只有 G04 的 10、15 分鐘方案**會真的換動作（F01-09 坐姿抬膝 → F01-11 站姿髖屈曲）。其餘 13 種方案都只顯示「維持（沒有套用進階）」。
- **AI 支援排序（R07）目前沒有作用**：F01-01～F01-20 的 `aiSupported` 全部為 true，所以排序實際上是「Direct／Supporting → R08 交替 → 動作編號」。

### 2-4 LLM 可以決定什麼、不能決定什麼

| 可以 | 不能 |
|---|---|

## 五、最影響推薦可信度的 3 個問題（依優先順序）

### 1. 限制 L01–L05 的排除靠字串比對，漏掉明顯相關的動作，而且會出現在唯一真正會發生的「進階」路徑上

> **2026-10-26 狀態**：只有其中的 G04＋L05＋F01-09 → F01-11 這個下一階段情境，已改為須經復健師檢視（暫時工程處理，見 `docs/F01_G04_L05_CASE_REVIEW.md` 第四節）。整體限制篩選**仍未修正**。G04 20 分鐘的首次推薦、患者取消勾選限制的政策、雲端規則未強制，仍是未解決缺口。

1. **什麼情境會發生**：患者在首次推薦勾選 L05「目前無法安全地單腳站立」，目標選 G04、時間 10 或 15 分鐘 → 首次得到 F01-09 坐姿抬膝。完成 6/6 天、再評估較快超過 3.12 秒、D5 沒有回報不適。
2. **使用者會遇到什麼結果**：D5 判定進階，把 F01-09 換成 **F01-11 站姿髖屈曲**，狀態為 `ready`，**患者可直接接受，沒有復健師看過**。F01-11 自己的資料寫「增進單腳站立動態平衡」「平衡感不佳…必須手扶」。（唯讀模擬已重現：`G04+L05 progress → F01-11`。）同樣地，L02（膝關節近期手術或急性腫脹）不會排除深蹲、坐姿起立等 6 個動作。
3. **屬於**：程式設計問題（用字串比對代替明確對照表）＋**需要專業確認**（哪些限制應排除哪些動作）。
4. **下一步與驗收**：
   - 做一張 5 × 20 的「限制 × 動作」對照表，列出目前結果與疑問格，交給物理治療師逐格確認（排除／可做但需扶持／不受影響）。
   - 確認後改由這張表決定排除，取代字串比對；注意事項原文只作顯示。
   - 驗收：
     - 每個 L × 動作的結果與確認表一致（逐格比對）。
     - G04 + L05 判定進階時，不會產生 F01-11（改為維持，或轉 `needs_review`）。
     - 沒有勾選任何限制時，首次推薦與 D5 結果和修改前完全相同。

### 2. 訓練週內的不適、吃力程度、未完成原因完全不進入下一階段判定

1. **什麼情境會發生**：患者一週內有 3 天每日回報「有不舒服」或「很吃力」，但在 D5 狀況確認時回答「沒有新的或加重的不適」（例如當天已不痛，或誤解題意）。
2. **使用者會遇到什麼結果**：系統只看 D5 那一題。結果可能是「維持」或「進階」，狀態 `ready`，患者直接接受，復健師工作台不會列出這份提案（只列 `needs_review`、`no_auto`、`reviewed`）。復健師只能在病患頁另外翻每日回報才看得到。
3. **屬於**：程式問題（資料已收集，卻沒有接到判定或提醒）＋產品政策需決定（每日不適要不要觸發專業確認）。
4. **下一步與驗收**：
   - 最小做法：D5 狀況確認頁列出本週每日回報摘要（哪幾天回報不適、很吃力、未完成原因），讓患者看著回答；同時把這份摘要放進復健師的 D5 卡片。
   - 若決定要更保守：本週任一天回報「有不舒服」時，安排一律轉 `needs_review`（只是路由，不新增門檻；需先確認政策）。
   - 驗收：
     - 有每日不適回報的週期，D5 頁和復健師卡片都顯示日期與內容。
     - （若採保守政策）同一週期即使 D5 答「沒有」，也不會是 `ready`。
     - 沒有任何每日回報的週期，結果與修改前相同。

### 3. 「進階／維持」的依據不足，而且進階幾乎只是標籤，訓練量完全沒有調整機制

1. **什麼情境會發生**：任何完成 6/6 天且再評估較快的患者。
2. **使用者會遇到什麼結果**：
   - 判定用的 3.12 秒來自不同族群（日本機構肌少症長者、人工計時）的研究，原文未核實，ReMotion 鏡頭計時自己的誤差不知道；「較快 × 6/6 → 進階」等組合沒有任何來源。
   - 除了 G04 的兩個方案，進階都只顯示「維持（沒有套用進階）」，下一週和上一週完全一樣；組數與次數從不調整，預設量本身也找不到依據（多數「待補」）。
   - 結果：系統說「進階」，患者感受不到任何變化；或者在量測誤差範圍內被判為進步。
3. **屬於**：**需要專業確認**（變化分類與矩陣、訓練量規則）＋資料不足（本系統的重測誤差）。不是程式錯誤，程式照規格運作。
4. **下一步與驗收**：
   - 核實 Yin et al. (2023) 原文（數值、信賴水準、施測方式、族群），並請專業人員決定是否沿用。
   - 規劃一次小規模重測（同一人、同一天或隔日，兩次鏡頭量測），估計 ReMotion 自己的誤差。
   - 在確認前，畫面上把「進階（沒有套用）」改成更直白的說明（例如「條件達到，但目前沒有已確認的下一階動作，下週維持」），避免誤解。這只改文字，不改判定。
   - 驗收：來源核實紀錄寫進規格檔；重測結果有樣本數與方法；文字修改後，判定與安排的 MD5 和修改前一致。
