## 3. 模擬器驗證

**確認連到的是模擬器，而不是正式專案**
- 專案 ID 是 `demo-remotion`。Firebase 對 `demo-` 開頭的專案只允許離線模擬，不連任何真實專案。
- 連線位置固定為 `127.0.0.1:8080`。
- R-S 腳本會先做預檢，輸出記錄在檔案中：
  `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 GCLOUD_PROJECT=demo-remotion ping="Ok"`
- 預檢沒有通過，腳本就直接中止，不執行任何案例。
- 載入模擬器的規則，是目前 `firestore.rules` 的複本，MD5 一致（`8fcfb3c5…`）。

**負向案例真的有在檢查**
- `assertFails` 只在收到「權限不足」時才算通過。
- 正向案例（例如「追加第二筆回報」）通過，代表規則中的清單前段比較 `after[0:n] == before` 能夠正確執行，不是因為語法錯誤才被拒。

**App 實際的寫入順序與復健師查詢**
- `results/08-…` 的 APP 系列，使用**真正的** `functionalAssessmentService` 產生的紀錄，依照 App 的順序寫入，每次都是整份文件：
  - 五次坐站：建立 → 完成 → 回報 → 第二次回報 → 只更新標記
  - 肩部評估：建立 → 動作結果 → 完成
- 復健師用與 `storageService` 相同的三條件查詢，取回 2 份紀錄。
- 寫入後讀回，原量測結果完全沒變，兩筆回報都保留。
- **限制**：關聯標記是依 `currentRelationStamp` 的規則**在腳本中複製**的。`storageService` 本身沒有在模擬器中執行，因為 App 的 Firebase 設定固定連到正式專案，見第 6 節。
