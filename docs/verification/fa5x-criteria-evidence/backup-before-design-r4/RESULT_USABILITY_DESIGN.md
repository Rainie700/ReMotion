1. 新增第 1 節「信任邊界查核」：列出五次坐站紀錄在雲端可被寫入的實際範圍，並區分「規則檔直接寫的事實」與「依規則推論、尚未驗證」。

### 1.2 依規則推論、**尚未驗證**的能力

這些推論只依據**專案中的 `firestore.rules`**，有三點都還沒確認：
- 線上專案（`.firebaserc` 中的 `remotion-2026`）實際部署的規則，是否與這個檔案相同。
- 沒有在 Firestore 模擬器上測試。
- 沒有用真實帳號嘗試。

在 F4 的規則下，任何一個已登入的帳號，只要直接使用 Firebase SDK（不經過 App 的畫面），應該能夠：

| 能力 | 推論依據 |
|---|---|
| **讀取所有人的五次坐站紀錄**，包括列出整個集合 | F4 的 read 包含 get 與 list。即使 ID 是隨機的（F8），也能用列出的方式取得 |
| **新增別人的紀錄**：寫入一份 `patientId` 為他人的文件 | F4 沒有檢查 `patientId`。對方下次登入時，會被 F3 的查詢載入 |
| **修改或刪除既有結果**，包括 `result.status`、`totalDurationMs` | F4 允許 update 與 delete；F2 是整份覆寫 |
| **追加或偽造條件回報**，包括把 `source` 寫成任何值 | 回報如果存在 session 上（本設計的做法），就受 F4 管轄 |
| **偽造示範標記**：寫入 `demoSynthetic: true` | 同上 |

**這不是本設計新造成的問題**：現有的量測結果本身就同樣能被改寫。本設計只是不能假裝條件回報比量測結果更可信。

### 1.3 「服務層檢查」是什麼

- 第二版說的「服務層統一執行」，指的是 `js/data/*.js`。這些檔案都**在使用者的瀏覽器中執行**（F7）。
- 它能保證「**經由 App 操作**時，所有入口套用同一套規則」，防止 App 自己的程式誤用資料。
- 它**不能**防止有人修改本機資料、修改瀏覽器中的程式，或直接寫入 Firestore。
- 文件與程式註解中都**不得**把它描述成權限保護、防竄改或雲端驗證。
- 要真正保護資料，需要收緊 Firestore 規則或加入伺服器端驗證。兩者都列在待辦（第 8 節 T1）。

### 1.4 結論

- 條件回報的所有來源（本人、照顧者、復健師）在目前架構下**都只能視為「使用者提供的聲明」**，無法證明是誰寫的，也無法證明內容沒被修改。
- 因此條件回報只能影響「顯示」與「描述性比較」，**不能解鎖任何自動進退階**。

## 2. 現況摘要（第二版已查證，這裡只列重點）

- 每次測試結束，session 的 `status` 一律是 `"completed"`；真正的結果在 `result.status`。
- 目前沒有任何條件欄位。用手、有人協助、條件未知，都被當成「完成」，因此會流進前後比較、Phase C、新週期與 D5。
- 有進行中的週期時，不能建立新週期（`trackingCycleService.js:164-165`）；週期只有完成再次評估才會結束。
- D5 判為「不自動判定」時，程式在讀取復健師審閱之前，就已經決定「不安排」（`d5Arrangement.js:139`）。
- 在「不自動判定」頁和已完成週期的首頁卡片上，都沒有「重新評估」的入口。
- 重新做一次五次坐站，再進入 Phase C，就能建立新週期（`app.js:15247`）。這條路已經存在，只是沒有入口。

## 3. 資料模型（四層，與第二版相同，但限縮來源）

| 層 | 內容 | 存放位置 |
|---|---|---|
| ① 機器判定 | 完成 5 次、未完成、量測無效 | 既有的 `session.result`，**不動** |
| ② 條件回報 | `armsUsed`、`physicalAssistance`：值為 `no`、`yes` 或 `unknown`。`chairHeightCm`：數字或 null。`sameChairAsBaseline`：`yes`、`no`、`unknown` 或 `not_applicable` | 新增 `session.conditionReports[]`，與 `result` 平行，只會往後新增 |
| ③ 回報來源 | 本批只寫入 `self_report`；照顧者代答時寫入 `caregiver_report`。兩者都由受測者帳號寫入，都屬於**使用者聲明** | 每一筆回報中 |
| ④ 使用資格 | 第 4 節的三種資格 | **不儲存**，讀取時推導；不覆蓋 ①② |

**通用規則**
- 沒有回報、欄位缺漏或值不合法，一律視為 `unknown`，**不推定為 `no`**。
- 表單不預先選取任何選項，「不確定」是正式選項。
- 補答或改答時新增一筆；判讀以最後一筆為準，舊的都保留。
- 多個問題同時列出，不會只剩一個。問題代碼與第二版 3.4 節相同。

**本批限縮來源**
- **不接受** `synthetic_demo`：讀到時只顯示「展示合成資料」，在資格判斷上視為 `unknown`。原因是示範標記同樣可以被偽造（1.2）。
- **不提供**復健師確認。

## 4. 三種使用資格

| 資格 | 條件 | 用在哪裡 | 不成立時 |
|---|---|---|---|
| **A. 可顯示** | 機器判定完成 | 結果頁、首頁追蹤卡顯示秒數 | 不顯示秒數（未完成、量測無效維持現狀） |
| A 的標題 | 條件回報為「沒用手、沒協助」時，標「完成時間（依使用者回報的條件）」；其他情況標「觀察時間」，並寫出原因（條件未回報、有用手、有協助、不確定） | | |
| **B. 可比較**（描述性） | 雙方都可顯示、量測版本同組、雙方都回報「沒用手、沒協助」、椅子可比 | 前後比較頁顯示差異，並註明「依使用者回報的條件，僅供參考，不作為自動調整依據」 | 不計算差異，只把兩個時間並列（沿用既有的 `historical` 顯示），並列出問題 |
| **C1. 可用於初次推薦**（Phase C） | 機器判定完成、量測版本是目前版本、回報「沒用手、沒協助」 | 儲存初次訓練建議、建立新週期、建立下一週期基準 | 拒絕，並列出問題 |
| **C2. 可用於 D5 自動進退階** | **本批中，任何條件回報都無法滿足。** 需要可信的確認途徑（待辦 T1、T2） | D5 的 GATE-VALIDITY | 前後比較回傳 `eligible: false`，D5 依既有規則判為 R001 不自動判定。**D5 程式不改** |

**實作上怎麼把 B 和 C2 分開**
- D5 只讀 `comparison.eligible`（`f01ProgressionDecision.js:509`）。
- 所以 `buildTrackingComparison` 在本批的做法是：
  - `eligible` **一律為 `false`**，代表「不能作為 D5 的依據」。
  - 符合 B 的情況，另外附上 `descriptive` 物件（差異與文字），只給比較頁顯示。
  - 第 5 節 Q1 有其他選擇。

**C1 允許使用者聲明的理由**
- Phase C 只用「是否完成」作為進入條件，不從秒數推導分級或門檻（`app.js:2050-2065` 的註解，以及 `f01GoalRecommendation.js` 的 R00）。
- 它不是進退階。
- 仍然要求聲明「沒用手、沒協助」，是因為依 PDF，需要用手或協助就屬於「依標準程序無法完成」。
- 是否接受這個做法，見第 5 節 Q2。

**再次評估連結週期**：維持只看機器判定完成，讓週期一定能結束，不會卡住。
