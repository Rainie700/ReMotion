## 2. 現況（經查證）

### 2.1 資料

- 每次測試結束，不論結果，session 的 `status` 都寫成 `"completed"`（`app.js:7124` 起；`functionalAssessmentService.js:164-173`）。
- 真正的結果寫在 `result.status`：`completed`、`incomplete` 或 `invalid`。
- 舊紀錄沒有 `result.status`：只要有 5 次而且有時間，就推定為完成（`app.js:6502-6508`；`trackingCycle.js:78-82`）。
- 目前**沒有任何欄位**記錄是否用手、是否有人協助、椅子條件，或由誰確認。

### 2.2 各種情況的現行處理

| 情況 | 結果頁 | 前後比較 | Phase C | 新週期／下一週期基準 | D5 |
|---|---|---|---|---|---|
| 機器判定完成 | 顯示正式時間 | 雙方都完成、量測版本相容才比較 | 可以 | 可以 | 依比較結果 |
| 用手或有人協助（PDF 的 unable） | **被當成完成** | **被當成完成** | **被當成完成** | **被當成完成** | **被當成完成** |
| 量測無效 | 不給時間 | 不比較 | 阻擋 | 阻擋 | 不連結週期 |
| 未完成 | 只顯示已完成次數 | 不比較 | 阻擋 | 阻擋 | 不連結週期 |
| 條件未知 | **被當成完成** | **被當成完成** | **被當成完成** | **被當成完成** | **被當成完成** |

### 2.3 本版新查證的事實

1. **有進行中的週期時，不能建立新週期**
   - `createOrGetTrackingCycle` 遇到另一個進行中的週期，會回傳 `another_active_cycle`（`trackingCycleService.js:164-165`）。
   - 「進行中」的定義是還沒有連結再次評估（`trackingCycleService.js:89-91`）。週期**沒有到期或放棄的機制**，只有完成再次評估才會結束。
2. **D5「不自動判定」時，復健師的審閱無效**
   - `resolveD5Arrangement` 遇到 `no_auto_decision` 時，在讀取復健師審閱之前就直接回傳 `no_auto`（`d5Arrangement.js:139`）。
   - 只有 `ready` 或 `reviewed` 能被接受（`d5Arrangement.js:169`）。
   - 所以在現行程式中，**復健師無法替一份「不自動判定」的提案安排下一週期**。
3. **「不自動判定」頁面沒有重新開始的入口**
   - 只有「返回首頁」「稍後確認」「修改狀況確認」三個按鈕（`app.js` 中 `d5ProposalPage` 的 `noAuto` 分支，約 16307 行）。
   - 「修改狀況確認」會重新跑 D5，而且比較會即時重算（`trackingCycleService.js:617, 641`）。
4. **已完成週期的首頁卡片沒有重新開始的入口**
   - 首頁卡片只有「查看前後比較」（`trackingCycle.js:178-191`）。
   - 有週期存在時，首頁的「開始自主復健」區塊會被週期卡取代（`app.js:12245` 起）。
5. **確認來源目前無法被信任**
   - `functionalAssessmentSessions` 任何已登入的帳號都能讀寫（`firestore.rules:138-146`）。
   - 所以寫在 session 上的「復健師確認」，無法證明真的出自有關聯的復健師。
   - 有關聯檢查的寫入路徑，目前只有 `d5TherapistReviews`（`firestore.rules:125-133`）。
6. **示範資料的標記方式不一致**
   - patient00 六週歷史會在紀錄上標 `demoSynthetic: true` 與 `demoBatch`（`scripts/demo/patient00History6w/buildHistory.mjs:16, 223`）。
   - 本機 D5 示範資料改用獨立的儲存前綴 `remotion_localdemo_`（`storageService.js:15-19`）。
   - 頁面上的標示依據是 `isDemoSynthetic(record)`（`js/ui/demoSyntheticLabel.js:15`）。

## 3. 四層資料模型（取代第一版的「標準完成」）

| 層 | 回答的問題 | 存在哪裡 | 是否會改變 |
|---|---|---|---|
| ① 機器判定 | 系統偵測到什麼（完成 5 次、未完成、量測無效） | 既有的 `session.result`，**完全不動** | 不會。測試結束後就固定 |
| ② 條件回報 | 有沒有用手、有沒有人協助、椅子條件 | **新增** `session.conditionReports[]`，與 `result` 平行，只會往後新增 | 只能新增，不能修改或刪除 |
| ③ 確認來源 | 誰提供這份回報 | 每一筆回報中的 `source` | 跟著該筆回報 |
| ④ 下游使用資格 | 這筆結果可以拿來做什麼 | **不儲存**，每次讀取時由純函式推導 | 回報或規則改變後，重新推導就會不同 |

### 3.1 ① 機器判定

- 沿用 `getFa5xResultStatus` 與 `isCompletedFiveTimesSitToStandResult`，舊紀錄的推定方式也不變。
- 對外名稱：「系統判定：完成 5 次」「系統判定：未完成」「量測無效」。
- **不使用**「標準」「有效」「正確」等字眼。系統判定完成，只代表偵測流程走完，不代表計次或計時準確。

### 3.2 ② 條件回報（與量測分開保存）

```js
session.conditionReports = [            // 與 session.result 平行；只會往後新增，不會修改舊的
  {
    schemaVersion: "fa5x-condition-report-1",
    armsUsed: "no" | "yes" | "unknown",
    physicalAssistance: "no" | "yes" | "unknown",
    chairHeightCm: number | null,
    sameChairAsBaseline: "yes" | "no" | "unknown" | "not_applicable",
    source: "self_report" | "caregiver_report" | "synthetic_demo",   // 見 3.3
    reportedBy: "帳號 ID",
    reportedAt: "ISO 時間",
  },
];
```

- 寫入只能透過新的服務方法 `functionalAssessmentService.appendFa5xConditionReport(sessionId, report)`。這個方法**只會在 `conditionReports` 後面新增一筆，不碰 `result`**。
- 判讀時以最後一筆為準；以前的紀錄全部保留，方便追查。
- **未知不能當成沒有發生**：
  - 沒有任何回報、欄位缺漏、值不合法，一律視為 `unknown`。
  - 表單不預先選取任何選項，「不確定」是正式選項。
- 事後回報（`reportedAt` 晚於量測當天）會被標記為 `retrospective`。是否接受事後回報，見【待決定】P3。

### 3.3 ③ 確認來源

| source | 誰寫入 | 本批是否接受 |
|---|---|---|
| `self_report` | 受測者本人的帳號 | 接受（是否足夠，見【待決定】P1） |
| `caregiver_report` | 受測者的帳號，由在場的家人或照顧者代答 | 接受（同 P1） |
| `synthetic_demo` | 示範資料產生器 | **只在示範紀錄上接受**，見 5.3 |
| 復健師確認 | 需要有關聯檢查的寫入路徑，例如比照 `d5TherapistReviews` | **本批不做**。session 這個集合目前誰都能寫，無法證明來源（見 2.3 第 5 點） |

來源只代表「由誰回報」，不代表內容已被驗證。

### 3.4 ④ 下游使用資格（推導，不儲存）

`deriveFa5xUsability(session, { context })` 回傳：

```js
{
  measurement: "completed" | "incomplete" | "invalid",   // 來自 ①
  conditions: { armsUsed, physicalAssistance, chairHeightCm, sameChairAsBaseline, source, retrospective } | null,  // 來自 ②③
  issues: [ ... ],                 // 所有同時存在的問題，不只一個
  primaryLabel: "...",             // 只用於畫面標題，依優先順序挑一個；其他問題仍列在 issues 中
  eligibility: { observedTime, phaseC, newBaseline, nextBaseline, reassessmentLink, trend },
}
```

`issues` 的代碼可以同時存在多個：

| 類別 | 代碼 |
|---|---|
| 量測 | `measurement_invalid`、`measurement_incomplete` |
| 量測版本 | `measurement_version_not_current`（沿用 `fa5xMeasurementCompatibility.js`） |
| 條件 | `arms_used`、`arms_unknown`、`assistance_given`、`assistance_unknown`、`no_condition_report` |
| 來源 | `source_not_accepted`（例如合成來源出現在非示範紀錄上）、`retrospective_report`（提示用，是否阻擋見 P3） |
| 成對比較時才檢查 | `chair_not_comparable`、`measurement_version_mismatch` |

範例：一筆 1.0 版、沒有任何回報的舊紀錄，會**同時**有 `measurement_version_not_current` 和 `no_condition_report` 兩個問題，不會只顯示其中一個。

**畫面標題的優先順序**（只影響標題，不刪除任何 issue）：

量測無效 → 未完成 → 有用手或有人協助 → 條件未回報或不確定 → 量測版本不是目前版本 → 「完成 5 次｜條件已回報」

最後這個標題是所有問題都排除時才使用，**取代第一版的「標準完成」**。

## 4. 使用資格規則

| 用途 | 條件（全部成立才可以） | 不成立時 |
|---|---|---|
| 顯示觀察時間 | 量測為完成 | 不顯示時間（維持現狀） |
| 顯示為「完成時間」 | 量測完成，而且沒有任何條件或來源問題 | 改標「觀察時間（條件未回報／有用手或協助）」。有用手或協助時是否顯示時間，見【待決定】P2 |
| Phase C（儲存訓練建議） | 量測完成、量測版本是目前版本、用手 = no、協助 = no、來源被接受 | 拒絕儲存，回傳 `fa5x_not_eligible` 與問題清單 |
| 新週期基準 | 同 Phase C | 拒絕，回傳 `baseline_not_eligible` 與問題清單 |
| 下一週期基準（新做或沿用再次評估） | 同 Phase C | 拒絕 |
| 作為再次評估連結到週期 | 量測完成（**維持現狀**） | 不連結（維持現狀） |
| 前後比較 | 雙方都符合「Phase C 條件」、量測版本同組、椅子可比（【待決定】P4） | 不比較，只把兩個時間並列（沿用現有的 `historical` 顯示），並列出問題 |
| D5 自動判定 | 前後比較成立（**D5 程式不改**） | 判為 R001 不自動判定（現有行為） |
| 功能趨勢 | 與「前後比較」中的單筆條件相同，而且屬於目前的量測版本組 | 不畫進趨勢線，另外顯示「另有 N 筆紀錄未列入趨勢」 |

**為什麼「作為再次評估連結到週期」維持只看量測完成**
- 週期只有完成再次評估才會結束（2.3 第 1 點）。
- 如果再次評估也要求條件，週期可能永遠無法結束，使用者會卡住，也不能建立新週期。
- 所以讓週期照常結束，改由比較與 D5 的規則把關。

### 5.2 歷史資料相容政策

| 歷史資料 | 處理方式 |
|---|---|
| 舊的五次坐站紀錄（沒有 `conditionReports`） | **不改寫、不補值**。讀取時推導出 `no_condition_report` |

| 已完成週期的比較頁 | 比較是即時重算的，所以舊的比較在新規則下會變成「不成立，兩個時間並列」。**這會改變使用者以前看過的畫面**，見【待決定】P5 |

### 5.3 示範資料政策（不能冒充真實確認）

- 示範資料只能寫入 `source: "synthetic_demo"` 的回報，而且該筆回報與 session 都要帶有 `demoSynthetic: true`。
- `synthetic_demo` 只在以下兩種紀錄上被接受：
  - session 本身是 `isDemoSynthetic(session) === true`
  - 本機示範資料（`isLocalDemoStorage()`）
- 其他紀錄上若出現 `synthetic_demo`，一律視為 `source_not_accepted`，**不會被當成真實回報**。
- 頁面上沿用既有的「展示合成資料」標示（`DEMO_SYNTHETIC_TEXT`）。
- 三個示範資料產生器需要配合修改：`js/dev/patient00Showcase.js`、`js/dev/localD5Demo.js`、`scripts/demo/patient00History6w/buildHistory.mjs`。
  - patient00Showcase 的五次坐站紀錄目前是否帶有 `demoSynthetic`，**沒有查證**，實作前要先確認。
  - 沒有標記的話，必須先補上標記，才能使用合成回報。
- 已寫進雲端的示範資料，不會被追溯修改。要等重新產生示範資料時才會有回報，所以在那之前，示範帳號會顯示為「條件未回報」（【待決定】P6）。

### 5.4 對既有測試的影響（必須事先說明）

- 服務層一律生效之後，建立週期、比較、D5、趨勢的既有測試，夾具（測試用資料）都需要加上明確的條件回報。
  - 用到 `createOrGetTrackingCycle` 的測試檔有 19 個。
  - 用到 `evaluateD5Proposal` 的有 10 個，用到 `getTrackingTimeline` 的有 9 個。
  - 其他還有比較、趨勢等測試。
- 做法：提供一個測試輔助函式，在夾具中附加 `source: "self_report"` 的回報，並在測試裡明確說明這是測試夾具。
- **不能放寬任何斷言**。每個被修改的測試檔都要列進修改清單。
- 另外新增測試：沒有回報時一定會被阻擋。

## 6. 舊基準被阻擋後怎麼接續（經查證）

| 情境 | 現行程式能否接續 | 本批最小補充 |
|---|---|---|
| A. 進行中的週期，基準是舊紀錄 | 可以繼續訓練。到了再次評估時，只要量測完成就會連結並結束週期（`trackingCycleService.js:250-275`）。之後比較不成立，D5 為 R001 | 無 |
| B. 補回報後重新判定 | **可行**。補回報後，在 D5 頁按「修改狀況確認」，就會用即時重算的比較重新判定（`trackingCycleService.js:617, 641`；`evaluateD5Proposal` 在提案未接受前可以重算） | 結果頁提供「補充測試條件」入口。舊基準能否用事後回報解鎖，見 P3 |
| C. 重新建立基準 | **可行，但沒有入口**。週期結束後就不再是進行中，重新做一次五次坐站並回報條件，再進入 Phase C，`createOrGetTrackingCycle` 就會建立新週期（`app.js:15247`） | 在 D5「不自動判定」頁和已完成週期的首頁卡片，加一個按鈕「重新進行五次坐站，建立新的追蹤」，導向 `goFiveTimesSitToStandAssessment()`。只加入口，不加流程 |
| D. 週期進行中就想重建基準 | **不可行**。有進行中的週期時，新週期會被 `another_active_cycle` 擋下；而且沒有放棄週期的機制 | 不在本批。使用者只能先完成再次評估（任何量測完成的結果都能結束週期），再走情境 C。要不要加「結束週期」功能，見 P7 |
| E. 由復健師安排下一週期 | **不可行**。「不自動判定」在讀取復健師審閱之前就被判為 `no_auto`（`d5Arrangement.js:139`） | 不在本批，因為要改就得動 D5 安排規則。替代路徑是情境 C，見 P8 |
| F. 沿用再次評估作為下一週期基準 | 不會卡住。比較成立時，雙方都已符合資格，可以沿用；比較不成立時，D5 是 R001，根本走不到沿用這一步 | 無 |

結論：只要補上情境 C 的兩個入口按鈕，就**不會有永久卡死的週期**。最壞的情況是：完成再次評估 → D5 不自動判定 → 重新評估並回報條件 → 建立新的週期。代價是失去 D5 的「沿用目標、下一階段」接續，改成從 Phase C 重新選目標。

## 7. 功能趨勢（統一範圍）

- 第一版只寫「趨勢只收 E」，而且是用開關控制；本版改為與前後比較使用**同一個單筆資格函式**，一律生效。
- 規則：量測完成、量測版本是目前的版本組、用手 = no、協助 = no、來源被接受。
- 不符合的紀錄不畫進趨勢線，頁面顯示「另有 N 筆紀錄未列入趨勢（條件未回報或量測方式不同）」，紀錄本身仍可在歷史中查看。
- 這也順帶處理了第一版提到的問題：1.0 與 1.1 的紀錄被畫在同一條線上。
- 影響：所有歷史紀錄都會從趨勢線上消失，直到補上回報（P3、P5）。
- **冒險關卡（`f01AdventureProgress.js:45`）本批不改**：它記錄的是「完成了一次評估」這個進度，不是比較時間。這一點列為已知差異，不擴大範圍。

## 11. 尚需決定的政策

| # | 問題 | 本設計的預設值 |
|---|---|---|
| P1 | 本人或照顧者回報「沒用手、沒協助」，就足以進入比較與推薦嗎？還是要復健師確認？如果要復健師確認，需要先建立有關聯檢查的寫入路徑，本批沒有 | 接受 |
| P2 | 有用手或有人協助時，要不要顯示觀察時間？要不要在資料或治療師端標成 PDF 的「0 秒」？ | 顯示「觀察時間（非標準測試成績）」，不顯示 0 秒 |
| P3 | 事後補回報（特別是舊基準）可以解鎖比較嗎？ | 可以，但標示「事後回報」。如果不接受，舊基準的週期只能走第 6 節情境 C |
| P4 | 椅子可比的規則：只靠「同一張椅子：是」可以嗎？椅高要完全相同，還是允許誤差？不知道椅子條件時要阻擋嗎？ | 回答「同一張」或兩邊椅高相同才算可比；不知道就阻擋 |
| P5 | 以前已經顯示過的比較與趨勢，在新規則下會變成不成立或消失。可以接受嗎？還是只對新規則生效之後的週期適用？ | 一律適用。如果改為只適用新週期，就等於把「未知」當成「沒有發生」，與本設計的原則衝突 |
| P6 | 已在雲端的示範帳號，要重新產生資料嗎？在那之前顯示「條件未回報」可以接受嗎？ | 接受顯示「條件未回報」，等重新產生 |
| P7 | 要不要加入「結束目前週期」的功能，讓使用者在週期中途就能重建基準？ | 不加，本批不擴充 |
| P8 | 「不自動判定」時，要不要開放復健師安排下一週期？這需要修改 D5 安排規則 | 不開放；改用重新評估的路徑 |
| P9 | 「未完成」是否要再問原因，用來區分做不到和中斷？ | 不問；維持「原因未確認」 |
| P10 | 冒險關卡要不要也改成要求符合資格？ | 本批不改 |
