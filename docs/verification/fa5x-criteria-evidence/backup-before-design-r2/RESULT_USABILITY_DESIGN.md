## 2. 現況：四種情況在各處怎麼處理

### 2.1 資料怎麼存

- `finalizeFa5xAssessment`（`app.js:7124` 起）在每次測試結束時，**不論結果是完成、未完成或無效**，都呼叫 `completeSession`，所以 session 的 `status` 一律是 `"completed"`（`js/data/functionalAssessmentService.js:164-173`）。
- 真正的結果寫在 `result.status`，取值為 `completed`、`incomplete` 或 `invalid`。
- **「session 完成」不等於「測試完成」。**
- 舊紀錄可能沒有 `result.status`。這時兩個函式都依「有 5 次而且有時間」推定為完成：`getFa5xResultStatus`（`app.js:6502-6508`）和 `isCompletedFiveTimesSitToStandResult`（`js/data/trackingCycle.js:78-82`）。
- 結果中**沒有任何欄位**記錄是否用手、是否有人協助、椅子條件，或由誰確認。

### 2.2 四種情況的現行處理

| 情況 | 現行程式能否辨識 | 結果頁 | 前後比較（`trackingComparison.js:76-120`） | Phase C 訓練建議 | 新追蹤週期與下一週期基準 | D5 |
|---|---|---|---|---|---|---|
| **完成** | 可以（`result.status = completed`） | 顯示總時間 X.X 秒，「將作為後續比較依據」（`app.js:6638-6700`） | 雙方都完成、量測版本相容才比較 | 可以（`app.js:2066` 只看是否完成） | 可以（`trackingCycleService.js:143, 166, 787-788`） | 比較成立就進入矩陣；不成立是 R001 不自動判定（`f01ProgressionDecision.js:34, 509`） |
| **無法完成**（PDF 的 unable） | **不能**。沒有這個狀態；用手或有人協助會被當成「完成」 | 用手完成也顯示成正式時間 | 會被拿來比較 | 會被允許 | 會被允許 | 會進入矩陣 |
| **量測無效** | 可以（`invalid`） | 「本次無法建立有效結果」，不給時間，說明原因與重試建議（`app.js:6604-6633`） | 不比較（`isCompletedFiveTimesSitToStandResult` 為 false） | 阻擋（`app.js:2066`） | 阻擋 | 再次評估不會連結到週期，週期繼續等待（`trackingCycleService.js:262`），所以不會產生 D5 |
| 未完成（逾時或取消） | 可以（`incomplete`），但原因不明 | 「本次評估尚未完成」，顯示已完成幾次，不給時間 | 不比較 | 阻擋 | 阻擋 | 同上 |
| **條件待確認** | **不能**。沒有任何條件欄位，所有「完成」都被當成標準完成 | 一律顯示為正式時間 | 會被拿來比較 | 會被允許 | 會被允許 | 會進入矩陣 |

### 2.3 其他也讀取結果的地方

- **首頁追蹤卡**：基準時間只取完成的結果（`app.js:15591`）。
- **功能變化趨勢**：只取完成、而且時間大於 0 的結果（`functionalProgressService.js:24-30`）。
  - 另一個觀察：這裡**沒有檢查量測版本**，1.0 和 1.1 的結果可能出現在同一條趨勢上。這不在本設計範圍內，另列為待確認。
- **冒險關卡**：完成就算達成（`f01AdventureProgress.js:45-46`）。
- **D5 給 LLM 的輸入**：`measurementValid` 由 session 狀態、結果是否無效、是否有時間推得（`d5LlmRecommendation.js:62`）。本設計不修改它的結構。
- **「最近評估」入口與結果頁的預設紀錄**：取最新一筆 session，可能是無效或未完成的結果（`app.js:6572, 12228`）。結果頁會依狀態顯示對應文字，這一點沒有問題。

**結論**
- 「量測無效」與「未完成」的阻擋，現行做法已經正確。
- 缺口集中在兩種情況：**用手或有人協助（應為 unable）**，以及**條件未知**。這兩種現在都會被當成標準完成，流進前後比較、訓練建議、新週期與 D5。

## 3. 最少的確認欄位

### 3.1 欄位設計

只新增欄位，不改既有欄位，附加在 `result` 上：

```js
result.protocolConfirmations = [            // 只會往後新增，不會修改舊的；以最後一筆為準
  {
    version: "fa5x-protocol-confirmation-1",
    armsUsed: "no" | "yes" | "unknown",         // 起身時是否用手推椅面、扶手、膝蓋或其他物品
    physicalAssistance: "no" | "yes" | "unknown", // 是否有人扶或身體協助
    chairHeightCm: number | null,               // 不知道就是 null，不填預設值
    sameChairAsBaseline: "yes" | "no" | "unknown" | "not_applicable", // 只有再次評估與下一週期基準才需要回答
    source: "self_report" | "caregiver" | "therapist", // 由誰確認
    confirmedAt: "ISO 時間",
  },
];
```

**未知不能當成沒有發生**
- 缺少欄位、欄位不合法、沒有任何確認、歷史紀錄沒有這個陣列：一律視為 `unknown`，**絕不推定為 `no`**。
- 表單不預先選取任何選項，「不確定」是正式選項之一。
- 要補答或改答時，新增一筆紀錄，舊紀錄保留，方便追查。

**刻意不放進這次的欄位**（是否加入【需專業確認】）
- 靠背、扶手、背碰椅背、腿後側抵住椅子、起始是否靠椅背：
  - PDF 有提到，但不影響「能否比較」的最小判斷。
  - 加了會讓使用者負擔變重。
- 「未完成」的原因（做不到或被打斷）：可以之後另外加一題。在加入之前，「未完成」一律視為「原因未確認」。

### 3.2 確認入口（最小做法）

- 放在**結果頁**：完成但還沒有確認的結果，頁面頂端顯示「確認測試條件」卡片。
- `finalizeFa5xAssessment` 不改，結束後仍然在約 1 秒後跳到結果頁，原本的原始碼檢查不受影響。
- 已經有的結果，也可以從結果頁「補充測試條件」入口補填。
- 治療師端的複核入口不在這一批，是否需要【需專業確認】。

## 4. 結果分類與用途

### 4.1 分類規則

這是純函式 `deriveFa5xResultUsability(session)`，每次讀取時重新推導，**不寫回資料**。依序判斷：

| # | 分類 | 條件 |
|---|---|---|
| A | **量測無效** | `result.status = invalid` |
| B | **未完成（原因未確認）** | `result.status = incomplete` |
| C | **依標準程序無法完成** | 量測完成，而且最後一筆確認中 `armsUsed = yes` 或 `physicalAssistance = yes` |
| D | **條件待確認** | 量測完成，而且沒有確認、`armsUsed` 為 unknown，或 `physicalAssistance` 為 unknown。**所有歷史紀錄都屬於這一類。** |
| E | **標準完成（已確認）** | 量測完成，`armsUsed = no`，而且 `physicalAssistance = no` |

- 「量測完成」沿用現行的 `getFa5xResultStatus` 和 `isCompletedFiveTimesSitToStandResult` 規則，舊紀錄也一樣適用。
- 量測版本相容性另外檢查，維持不變（`fa5xMeasurementCompatibility.js`）。

### 4.2 各分類的用途

| 分類 | 結果頁顯示的時間 | 進入前後比較 | Phase C 自動推薦 | 新週期基準與下一週期基準 | 作為再次評估連結到週期 | D5 自動判定 |
|---|---|---|---|---|---|---|
| A 量測無效 | 不顯示（維持現狀） | 否 | **阻擋** | 阻擋 | 否（維持現狀） | — |
| B 未完成 | 不顯示，只顯示已完成幾次（維持現狀） | 否 | **阻擋** | 阻擋 | 否（維持現狀） | — |
| C 依標準程序無法完成 | 不顯示標準成績，顯示「依標準程序：無法完成（需用手／需協助）」；另外顯示「觀察時間 X.X 秒（非標準測試成績）」【需專業確認】 | 否 | **阻擋** | 阻擋 | 是（量測完成，週期照常關閉）【需專業確認】 | 比較不成立，所以是 R001 不自動判定 |
| D 條件待確認 | 「觀察時間 X.X 秒（測試條件待確認，尚不作為正式成績）」 | 否：只並列兩個時間，不計算差異（沿用現行版本不相容時的 `historical` 顯示方式） | **阻擋** | 阻擋 | 是（同上）【需專業確認】 | 比較不成立，所以是 R001 |
| E 標準完成 | 「完成時間 X.X 秒」（維持現狀） | 是，但還要滿足：雙方都是 E、量測版本相容、**椅子條件可比** | 可以 | 可以 | 是 | 依現行矩陣 |

**椅子條件可比**【需專業確認】
- 預設規則（滿足任一項即可）：
  - 再次評估回答 `sameChairAsBaseline = yes`
  - 雙方都填了 `chairHeightCm`，而且數值相同
- 其他情況（不知道、不同）：不進入比較，只並列時間，並寫明「椅子條件不同或未確認」。
- 椅高不在 43–45 cm：依 PDF p2 Q1，只記為「偏離標準椅高」並顯示出來，**不阻擋**。

**對 D5 的影響**
- D5 不需要改：比較不成立時，`buildD5Proposal` 原本就會判為 R001 不自動判定（`f01ProgressionDecision.js:509`）。
- D5 決策矩陣、LLM 輸入結構都不變。
- 預期的副作用：比較不成立時，LLM 拿到的 `changeSeconds` 為 null，這是現有路徑的既有行為。

### 4.3 尚需專業確認的規則（不自行當成臨床定論）

1. 本人自我回報「沒有用手、沒有協助」，就足以算 E 嗎？還是要治療師或照顧者確認？
2. C 類（用手或有人協助）要不要顯示觀察時間？PDF p1 允許另外記錄時間作為基線資訊，但「不算一次 5TSTS 測試」。
3. C、D 類的再次評估，要不要照常關閉追蹤週期？預設照常關閉，以免週期卡住；但比較與 D5 都不成立。
4. 椅子可比的規則：只靠「同一張椅子：是」可以嗎？椅高要完全相同，還是允許誤差？不知道椅子條件時，要不要阻擋比較？
5. 依標準程序無法完成時，資料或治療師端要不要標記成「0 秒」（照 PDF）？使用者端預設不顯示「0 秒」，以免被誤認為成績很快。
6. 「未完成」中的逾時（超過 60 秒）或使用者取消，要不要再問原因，用來區分「做不到」和「中斷」？
7. **歷史紀錄一律屬於 D（條件待確認）。** 這會讓**目前進行中的追蹤週期**在再次評估之後，比較不成立、D5 判為 R001。可接受嗎？要不要開放治療師補確認？
8. 示範資料（patient00、本機 D5 demo）原本沒有確認紀錄，加上新規則後，會從可比較變成待確認。要另外為示範資料補上確認（來源標為合成示範），還是接受示範資料顯示為待確認？
9. C 類使用者要怎麼安排訓練？本設計只阻擋自動推薦，不提出替代方案。
