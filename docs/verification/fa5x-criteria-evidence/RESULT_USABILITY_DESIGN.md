## A 批：紀錄與權限基礎

### A.1 目標

1. 記錄條件回報、來源與時間；結果頁清楚標示。
2. 歷史紀錄照常顯示。不可比較的結果不計算差異，也不連成趨勢線。這裡的「不可比較」只用**既有的定義**：
   - 機器判定不是完成

- 不阻擋初次推薦、建立週期或 D5。這些流程的行為與修改前相同。

### A.3 Firestore 權限設計（草案，必須用模擬器驗證）

```
match /functionalAssessmentSessions/{id} {
  // 讀：擁有者，或帶有「已接受關聯」標記的復健師（linked() 沿用既有函式，firestore.rules:21-27）
  allow read: if request.auth != null
    && (resource.data.patientId == request.auth.uid || linked(resource.data));
  // 建立：只能建立自己的；關聯標記必須是空的，或是自己的已接受關聯；
  //       不得帶示範標記；條件回報必須是空的
  allow create: if request.auth != null
    && request.resource.data.patientId == request.auth.uid
    && validRelationStamp(request.resource.data)
    && !('demoSynthetic' in request.resource.data)
    && reportsEmpty(request.resource.data);
  // 修改：只能改自己的；patientId 不變；有 result 之後 result 不能再變；
  //       條件回報只能追加 0 或 1 筆，舊的完全不變，新的那一筆 reportedBy 必須是自己、
  //       source 只能是允許的值；示範標記不能變；關聯標記必須合法
  allow update: if request.auth != null
    && resource.data.patientId == request.auth.uid
    && request.resource.data.patientId == resource.data.patientId
    && resultUnchangedOnceSet()
    && reportsAppendOnlyByOwner()
    && request.resource.data.get('demoSynthetic', null) == resource.data.get('demoSynthetic', null)
    && validRelationStamp(request.resource.data);
  allow delete: if false;   // App 本身沒有刪除五次坐站紀錄的流程（已查證）
}
```

**必須先在模擬器上確認的語法與限制**（尚未驗證）
- 「條件回報只追加、舊的不變」需要比較清單的前段，例如 `list[0:n] == old`。Firestore 規則是否支援這種寫法，要先確認。
- 規則無法逐一檢查陣列中的每個元素，所以設計成每次寫入最多追加一筆。
- 依關聯標記做讀取檢查時，查詢必須包含與規則對應的等式條件（比照現有的選用集合）。

**這個設計的已知限制**（推論）
- 每份紀錄只帶一組關聯標記，所以同一時間只有一位復健師讀得到。
- 轉介或更換復健師之後，病人的 App 要把**自己的**紀錄重新標記成新的關聯，舊的復健師就讀不到了。
- 標記之前的舊紀錄沒有關聯標記，復健師讀不到，要等病人的 App 補上標記（P3）。

### B.3 自動調整資格（B2）的條件

全部成立，`comparison.eligible` 才是 true：

1. 既有的比較條件全部成立：週期連結、雙方機器判定完成、量測版本同組（`trackingComparison.js:76-120`）。
2. 基準評估和再次評估**都符合** I6～I10。I4 與 I5 依角色調整：再次評估本來就是再次評估。
3. 椅子可比：再次評估回答「同一張椅子」，或兩邊椅高相同（P6）。
4. A 批規則已部署並驗證，所以回報作者是本人有雲端保證。
5. 信任政策 P1 允許以使用者聲明作為自動調整的依據。**P1 尚未決定**：如果 P1 決定「不允許」，B2 就永遠不成立，所有週期都只能走 B3，或重新評估。

### B.4 復健師另行安排（B3）

- **觸發時機**：D5 判為「不自動判定」（R001），原因不限，包括 B2 不成立。
- **流程**：
  1. 有已接受關聯的復健師，在復健師工作台看到這份提案。
  2. 復健師用既有的 `d5TherapistReviews` 提交安排。
  3. 病人接受。
  4. 依既有的交接規則建立下一週期。
- **最小修改**：
  - `js/data/d5Arrangement.js`：目前 `no_auto` 的判斷在讀取審閱之前（`:139`）。改成：遇到 `no_auto` 時，**如果有一份有效、而且沒有衝突的審閱**，就回傳 `reviewed`，標示「復健師另行安排（資料不足，未自動判定）」；沒有審閱時仍然是 `no_auto`。`d5.decision` 維持 R001，不改寫。
  - `js/data/d5TherapistReviewService.js`：清單與提交目前只接受 `needs_review` 和 `reviewed`（`:75, 130`），要加入 `no_auto`。
  - `app.js`：
    - D5「不自動判定」頁：有關聯復健師時，顯示「可由復健師安排下一週」或「等待復健師安排」；沒有關聯時，顯示重新評估的入口。
    - 復健師工作台：列出這類提案。
- **下一週期基準**：專業安排時，可以沿用同一天的再次評估作為基準，條件是機器判定完成、量測版本是目前版本（既有的交接規則）。**不要求條件回報**（P7）。不是同一天時，依既有規則需要重新評估。基準本身的使用資格不會因此改變，下一週的比較仍然重新判斷。
- **雲端規則依賴**：
  - 病人接受審閱過的安排時，`recommendationResults` 的 `reviewMatches` 會比對 `basis.decisionRuleId`（`firestore.rules:79-92`）。R001 是否能通過，要在模擬器中確認。
  - 專案中的 `scripts/demo/patient00History6w/rules/firestore.deployed-assumed.rules`，被描述為「推定目前已部署」的規則，裡面**沒有** `d5TherapistReviews` 的規則。所以線上到底能不能寫入復健師審閱，**尚未確認**（見依賴 D3）。
- **沒有關聯復健師的病人**：資料不足時沒有專業安排可走，只剩重新評估（P2）。

### B.5 啟用方式：全部完成並驗證後，一起啟用

- 開關關閉時，B 批的檢查都不生效，行為與 A 批完成後相同。
- 只有下列條件**全部**成立才開啟：
  1. A 批規則已部署並驗證（A.6 第 5 點）。
  2. 線上已能寫入 `d5TherapistReviews`（依賴 D3）。
  3. B 批驗收案例全部通過。
  4. P1、P2、P7 已決定。
- 開關開啟時，B1、B2、B3 與 B.2 的准入條件**同時生效**，不分次開啟。
