## 3. 最小修正

- 修改位置：`js/ai/exercises/sitToStand/assessmentSession.js` 中 `processRunning` 處理「追蹤中斷」的分支。
- **每收到一幀未追蹤的畫面**，就清除：
  - 還沒成立的站立確認幀數與它的候選起始時間（`standConfirm`、`standConfirmFirstAt`）
  - 還沒成立的坐回確認幀數與它的候選起始時間（`seatConfirm`、`seatConfirmFirstAt`）
- 逐幀紀錄的判定資訊多記一項 `pendingConfirmationsCleared: true`。
- **保留不變**：
  - 已完成的次數
  - 目前的動作狀態（起身中、站立、坐下中）
  - 峰值紀錄
  - 坐姿基準
  - 「開始」的計時起點
  - 中斷次數的計算
  - 1.2 秒的中斷上限與判為無效的規則
- **門檻沒有任何改變**：`FA5X_PARAMS` 的值、`FA5X_THRESHOLD_VERSION` 都維持原樣，`test:fa5x-gap-reset` G0 有檢查。

## 4. 版本、重播與前後比較的處理

| 項目 | 處理方式 |
|---|---|
| 演算法版本 | `FA5X_ALGORITHM_VERSION` 從 `fa5x-assessment-1.1` 改為 **`fa5x-assessment-1.2`**；門檻版本不變 |
| 量測相容性 | 1.2 是**獨立的版本組**（`fa5x_isotropic_gap_resets_confirmation`）。1.1 仍是已知、但不再是目前的版本組。**1.1 與 1.2 一律不可比較**；1.1 與 1.1、1.2 與 1.2 仍然可以比較 |
| 歷史資料 | **不改寫**。已存的 1.1 結果保留原版本，照常可以查看（`test:fa5x-compat` 2b） |
| 重播 | 重播工具原本就要求紀錄的演算法版本與目前的判定器相同。1.2 的紀錄能「重現成功」；1.1 的紀錄一律回報「不支援」，並寫明版本不同，**不會**用新的判定器去重播舊紀錄（`test:fa5x-gap-reset` G10） |

**對使用者的影響**（依既有規則推論；`test:fa5x-compat` 有驗證）
1. 以 1.1 結果作為基準、仍在進行中的追蹤週期：再次評估會用 1.2 量測。前後比較會**不成立**，只把兩個時間並列；D5 判為「不自動判定」（R001）。
2. 1.1 的結果**不能**再作為新週期或下一週期的基準，必須用 1.2 重新評估。
3. 已經建立的週期、提案與歷史結果都不受影響，也不會被改寫。

## 6. 剩餘限制

1. **「完全沒收到幀」沒有處理**：推論出錯或畫面停頓時，相機迴圈直接跳過那些幀（`squatCameraController.js`），判定器根本收不到。所以兩個已追蹤的幀之間即使隔了很久，仍會被視為連續。G8 用 800 ms 的時間跳躍，固定記錄了這個現況。依指示**沒有新增時間門檻**；如果要處理，需要另外決定一個以時間判斷的規則。
2. **新的漏算風險**：追蹤時斷時續、但真的完全站直或坐回的情況，現在可能永遠湊不滿連續 3 幀，結果被判為「未完全站直」，要多做一次，或者時間變長（見 S3）。修改前的錯誤方向剛好相反（不完整的連續也被接受）。哪一種方向比較接近真實，**需要真人實拍資料才能判斷**。
3. 確認幀數仍然是以「幀數」計算，實際時間會隨裝置的推論速度改變（既有限制）。
4. **以 1.1 為基準的進行中週期**，前後比較會不成立，D5 判為「不自動判定」（第 4 節）。這是「不默認新舊版可比較」的直接結果，需要讓使用者知道。
5. 先前兩批的瀏覽器驗證腳本（`fa5x-browser-local/browser/phase1-…`、`fa5x-result-wording/browser/phase2-…`），把 1.1 當成目前版本來建立週期。依指示保留原樣不修改；如果要重跑，必須先改用目前版本的欄位，否則會因「基準版本過舊」而失敗。本輪沒有重跑。
6. 已經錄下的 1.1 逐幀紀錄，現在都不能用目前的判定器重播。
7. 這些全部是合成資料的結果，**沒有證明真人準確度提升**。
