## 驗收中發現的問題與修正

1. **B4 重新整理後看不到復健師確認**（`hasReview=false`）。根因在**測試**，不是資料遺失：
   - 復健師確認後，模擬器中確實有 `f01InitialReviews/{id}`（B3）。
   - **已確認的事實**：原測試沒有等到集合載入完成、也沒有等到登入後的首頁準備好，就讀取畫面；修正「可以開始操作」的判斷條件後就通過了。
   - **這段說法的範圍（收尾輪更正）**：前一版寫成「Playwright 遇到非同步判斷式會直接成立」，這把單次觀察寫成了通用結論，已收回。目前能確定的只有以下幾點：
     - 本專案**沒有**包裝 Playwright，腳本直接呼叫 `page.waitForFunction`；
     - 在本腳本、Playwright 1.56.1 中，`page.waitForFunction(async () => false, null, { timeout: 2000 })` 不到 2 秒就結束（各次執行約 6～29 毫秒，`RUN_LOG` 的 OBSERVED 行），沒有等到逾時；
     - 本輪**沒有**查證官方 API 對非同步判斷式的處理方式，所以不對 Playwright 本身下結論。
   - 最小重現：任一已載入的頁面執行上面那一行，看它是否在 2 秒內結束。
   - 等待邏輯（輪詢載入狀態加上首頁出現）沿用前一輪已通過的版本，本輪沒有修改。
   - `getOptionalCloudLoadStatus` 在兩種情況回傳 `null`：沒有執行雲端載入時，以及 `hydrateCloudForUser` 還在第一階段（載入必要集合）時。
   - 改成輪詢實際狀態後：重新整理約 950 毫秒後三個集合都是 `loaded`；確認紀錄已在本機；指紋、basis 與照護關係都相符；安排狀態是 `reviewed`。
   - 剩下的失敗原因：`loaded` 是在 `hydrateCloudForUser` 結束時設定，但 app 的 `setSession`（設定目前使用者與首頁路由）要等它完成後才執行。測試在這兩者之間切換頁面，所以畫面上看不到目前使用者，顯示「還沒有訓練建議」，之後又被首頁路由蓋掉。真實使用者在 `setSession` 之前無法操作畫面。
   - **修正**：
     - 測試的就緒判斷改為「三個集合都已載入，而且 session 的首頁已顯示」，不使用固定等待秒數；
     - 修正 `storageService.getOptionalCloudLoadStatus` 註解中對 `null` 的說明（只改註解，不改行為）；
     - 沒有修改指紋、權限或資料。
2. **復健師端看不到病人新產生的安排**：復健師是在病人建立推薦之前登入的。app 只在登入或重新整理時載入雲端資料，沒有即時監聽；重新整理後就看得到（`RUN_LOG` 中的 OBSERVED 行）。這是現有行為，**沒有修改**。
3. **新增測試接線**：`app.js` 中的 `window.__emulatorFinishFa5xRun`，只有在 Vite 開發版、localhost 且網址帶 `?emulator=1` 時才定義。存下的結果標記 `emulatorSynthetic: true`，不改任何權限。正式版的 bundle 中仍有這段程式碼，但條件不成立，所以永遠不會定義這個函式（與既有的模擬器提示列相同）。

**「重新載入」的做法**
- 先送出本機尚未同步的寫入，再對目前的登入身分執行一次與登入時相同的 `storageService.hydrateCloudForUser`，然後重新繪製畫面、重新計算安排狀態。
- 不需要登出或整頁重新整理；沒有新增即時監聽、通知或背景輪詢。
- 載入中時按鈕停用；完成後顯示成功或失敗。
- 尚未送出的表單內容（存在 `state`）不會被清掉（R3）。
- 重新載入只更新資料：不會代替患者接受，也不會建立週期（R5）。

**驗收中發現的問題與修正**
- 離線時，雲端讀取不會失敗，而是一直等連線，按鈕會停在「載入中」。
- 修正：重新載入超過 15 秒就顯示更新失敗，並可以重試；如果那次載入之後還是完成了，狀態列會改成已重新載入。畫面上原本的內容會保留，並註明可能不是最新的（R6、R7）。

## 重現方式

1. 準備一個獨立的工具資料夾（不要用專案的 `node_modules`）：
   ```
   npm i firebase-tools@13.35.1 @firebase/rules-unit-testing@3.0.4 firebase@10.14.1 playwright@1.56.1
   npx playwright install chromium
   ```
   需要 Java 17 以上（本次使用 JDK 22）。
2. 把 `scripts/f01InitialReviewBrowserCheck.mjs` 與專案的 `firestore.rules` 複製到該資料夾，並加入 `firebase.json`：
   ```json
   {"firestore":{"rules":"firestore.rules"},"emulators":{"firestore":{"port":8080},"auth":{"port":9099},"ui":{"enabled":false}}}
   ```
3. 執行：
   ```
   REPO=<專案路徑> firebase emulators:exec --only firestore,auth --project demo-remotion "node f01InitialReviewBrowserCheck.mjs"
   ```
   腳本會自動啟動 Vite（`127.0.0.1:5173`）、建立模擬器帳號（`f01-*-<時間>@local.test`，密碼 `f01-local-only-123`），並把截圖存到本資料夾。

**手動操作的點選順序**（模擬器與 `npm run dev` 都啟動後，開 `http://127.0.0.1:5173/?emulator=1`，病人與復健師使用不同的瀏覽器設定檔）：

1. 病人：五次坐站結果頁 →「查看訓練建議 →」→ 選「加強髖部與骨盆穩定」→ 選「20 分鐘」→ 勾「目前無法安全地單腳站立」→「產生訓練建議 →」。
2. 復健師：個案頁 →「首次訓練安排待檢視」→「檢視並確認安排」→ 移除站姿髖屈曲、設定組數、填寫理由 →「確認這份安排」。
3. 病人：重新整理 → 訓練建議頁 →「接受這份安排」。
   - 同一天接受：第一週立刻開始。
   - 不同天接受：按「開始第一週基準評估 →」→「開始評估 →」，在相機頁完成評估。真實相機需要實際做五次坐站；在模擬器模式下也可以在開發者工具執行 `__emulatorFinishFa5xRun({...})` 代替。
